# 简历导入与自动分析链路

本文说明 Bohack 当前的简历导入、PDF 阅读、候选人识别和分析报告生成架构。目标是让后续接入 OCR、任务队列、更多模型或数据库时，可以保持前端交互和数据契约稳定。

材料评分 v1 已成为新评估入口，完整参数与新流程见 [SCORING_V1.md](SCORING_V1.md)。下文第 8.1 节六维评分描述保留为历史兼容记录，不代表新评估还在调用模型直接打分。

简历处理现已按职责拆分为可选择运行的多个 Agent；依赖、输入指纹缓存、重跑范围和接口见 [AGENT_PIPELINE.md](AGENT_PIPELINE.md)。

## 1. 设计目标与边界

导入一份 PDF 的结果不是单纯的文件复制，而是一个可追踪的候选人索引任务：

1. 保留原始 PDF，保证阅读器可以随时打开原文件。
2. 从 PDF 提取可检索文本，保留原始文本供分析和审计。
3. 从文本中提取最小候选人字段，用于左侧候选人列表。
4. 整理七类材料并按固定规则计算五维能力，保存材料及规则快照；可用模型生成初始文字报告。
5. 后续输入职位要求时，在同一候选人记录上生成岗位匹配报告。
6. 任何模型失败都不能破坏原文件，也不能伪造成功结果。

当前版本是本地优先架构：PDF、文本和分析缓存位于 `RESUME_DIR`，默认是 `.data/resumes`。模型 API Key 只由服务端读取。浏览器只访问本地 API，不直接接触密钥。

## 2. 端到端流程

```text
浏览器选择 PDF / 文件夹
        |
        v
POST /api/resumes  (application/pdf)
        |
        +--> 校验大小、文件头、文件名并写入 <RESUME_DIR>/<id>.pdf
        |
        +--> PDF.js Node 提取每页文本
        |       - CMap: pdfjs-dist/cmaps
        |       - 标准字体: pdfjs-dist/standard_fonts
        |
        +--> Agent 编排：candidate-profile
        |       - 只允许从原文提取 name/role/location/education/skills/summary
        |       - JSON 结构化输出
        |
        +--> Agent 编排：material-extraction -> score-calculation
        |       - 固定规则计算材料和能力分
        |       - 只使用简历原文，不做成果真实性核查
        |
        +--> Agent 编排：analysis-report
        |       - 使用简历 Skill
        |       - 不给岗位匹配分，不调用网页搜索
        |       - 输出概览、证据、信息缺口、建议追问
        |
        +--> 写入 <RESUME_DIR>/.metadata/<id>.json
        |
        +--> 返回 ResumeRecord
```

导入请求是同步请求，因此前端在模型链路结束前显示“正在识别”。这保证导入完成时左侧候选人、分析文档和持久化元数据一致；代价是模型较慢时导入按钮会等待。后续应将这一步迁移为异步任务，但保留同样的记录字段和状态。

## 3. 文件与元数据

每份简历有一个稳定的 `id`，由原始文件名片段、时间戳和随机短 ID 组成。原始 PDF 与元数据分离：

```text
.data/resumes/
  <id>.pdf
  .metadata/
    <id>.json
```

当前 `ResumeRecord` 的核心字段：

| 字段 | 用途 |
| --- | --- |
| `id` / `fileName` | 文件与 API 路由定位 |
| `text` | PDF 文本提取结果，作为模型输入和检索基础 |
| `name` / `role` / `location` | 左侧候选人卡片和详情头部 |
| `education` / `skills` / `summary` | 候选人基础画像 |
| `analysisReport` | 最近一次自动或手动分析报告 |
| `analysisStatus` | `complete`、`failed` 或 `unavailable` |
| `analysisError` | 最近一次失败的可读原因 |
| `analyzedAt` | 报告生成时间 |
| `scoreHistory` | 历史六维评分记录，原样保留 |
| `assessment` | 当前材料、因素积分、行动映射、五维能力与输入 / 规则快照 |
| `assessmentHistory` | 按时间追加保存的 v1 完整评估，独立于岗位权重 |
| `agentArtifacts` | 按 Agent 保存的输入指纹与输出，用于定向复用及增量重跑 |
| `extractionVersion` | 解析器升级后的缓存失效标记 |

`extractionVersion` 变更时，服务会重新提取已有 PDF 并刷新元数据。这个机制用于部署 CMap、OCR 或提示词升级，不需要用户重新导入文件。

## 4. 状态与失败处理

当前状态语义如下：

- `complete`：文本提取成功，并且初始分析报告已生成。
- `failed`：PDF 可保存和阅读，但模型字段提取或报告生成失败；`analysisError` 保留原因，前端显示“重试分析”。
- `unavailable`：没有配置模型服务，PDF 仍可阅读，候选人字段回退到文件名或默认值。

失败的处理原则：

1. 文件写入成功后才开始解析；解析失败会删除刚写入的 PDF，避免留下半条记录。
2. 模型失败不会删除 PDF，也不会把空字符串标记成成功报告。
3. 手动重试调用 `POST /api/resumes/:id/analyze`，只更新分析字段，不重复复制 PDF。
4. 读取目录时按 `extractionVersion` 判断是否需要重建索引。

## 5. API 契约

### `POST /api/resumes`

请求头：`Content-Type: application/pdf`、`X-File-Name: encodeURIComponent(originalName)`。

成功返回 HTTP `201` 和完整 `ResumeRecord`。导入过程包含文本提取和初始报告生成，因此返回时 `analysisStatus` 已有明确值。

### `GET /api/resumes`

扫描 `RESUME_DIR` 中的 PDF，读取或重建元数据，返回 `{ directory, resumes }`。该接口是工作台启动和刷新时的索引入口。

### `POST /api/resumes/:id/analyze`

请求体包含 `roleRequirements` 和 `question`，可选 `ocrText` 和 `streamProgress`。旧的 `includeResearch`、`webResearchEnabled` 参数会被拒绝。使用缓存的 `text` 或本次 OCR 文本先评估材料，再让模型解释同一份计算结果，成功后保存报告及 v1 评估历史。仅需评分时调用 `POST /api/resumes/:id/assessment`，可以不用模型。

竞赛、论文和项目仅从简历原文中提取并参与材料评分，不读取 `db/`，不调用搜索服务，也不判断候选人是否真实获奖、发表或参与。开启流式响应时，以 NDJSON 推送阶段、评分和报告正文，最终 `complete` 事件包含更新后的 `resume`；普通请求继续返回 JSON。停止分析或断开连接会取消请求。

### `POST /api/resumes/:id/agents/run`

请求体用 `agents` 数组列出要运行的 Agent，可选提供 `roleRequirements`、`question`、`reviewerFocus`、`force`、`useModel` 或 OCR 文本。服务端读取并复用 `agentArtifacts`，只运行指定 Agent 及缺失或失效的依赖。响应返回 `executed`、`reused`、各 Agent 输出及更新后的简历。断开连接会取消尚未完成的任务，取消或失败时不保存部分结果。

### `GET /api/resumes/:id/file`

只返回原始 PDF 流，阅读器使用 PDF.js 在浏览器内渲染。CMap 和标准字体由 Vite 静态目录提供，不混入 PDF 文件接口。

## 6. PDF 透明文字层与奖项遮罩

PDF 阅读器在原始画布上方维护一个透明的文字层。文字层使用 PDF.js `getTextContent()` 返回的每个文本项和 viewport 变换矩阵，将 PDF 坐标转换为浏览器 CSS 像素坐标。原始画布负责显示 PDF；文字层只负责选择和标注，不替换或重绘原文。

奖项识别是当前版本的轻量规则层：对文本项匹配中文奖项词、竞赛词和常见英文缩写，例如“奖”“金牌”“一等奖”“竞赛”“ACM”“ICPC”“CCF”“CSP”。识别结果只用于视觉提示，不代表语义判断，也不会改变候选人字段或分析报告。

遮罩交互只有一个左右拨动开关 `showAwardMask`（使用 `role="switch"`，视觉上不是复选框）：

- 开启：当前 PDF 中所有命中的文本项显示半透明黄色背景。
- 关闭：隐藏当前 PDF 的全部黄色背景，但保留透明文字层和原始 PDF。
- 开关只影响当前阅读器视图，不修改 PDF 文件、候选人元数据或分析报告。

渲染约束：

1. 标注层必须与对应页面 canvas 使用同一 viewport、缩放比例和输出像素比例。
2. 每个页面独立维护文本项，翻页和滚动只更新当前页指示器，不改变标注集合。
3. 文本项没有可用坐标时不创建标注，避免出现漂移的黄色块。
4. 规则命中数量仅作为界面提示，用户仍需阅读原始 PDF 核对奖项内容。

## 7. 模型分层

模型调用分为两个目的，不能混成一个不透明提示词：

1. `candidate-profile` Agent 调用 `extractCandidate`：低温度、JSON 输出、字段少、只读原文；用于列表展示。
2. `analysis-report` Agent 调用 `generateInitialReport` 或 `generateRoleReport`：按初始导入或岗位分析生成报告。
3. `analyzeResume`（`server/agent.ts`）：先调用 `server/scoring/pipeline.ts`，复用一次材料抽取及同一批 Skill 资料，计算 v1 画像后输出解释报告。通过 `server/analysis-response.ts` 统一处理流式进度、超时和取消。模型不再独立给六项能力打分。

导入产物及输入指纹保存在候选人元数据的 `agentArtifacts`。对已有候选人定向更新使用 `POST /api/resumes/:id/agents/run`；它只运行所选 Agent 和缺失/已失效的依赖，不会强制重跑整条 `analyzeResume` 链路。

三个阶段共享 `server/skills/resume-analysis.md` 的安全与证据规则，但输入和输出职责不同。任何阶段都将简历放在 `<resume>` 标记中，并把简历视为不可信数据，避免执行 PDF 中可能出现的提示注入内容。

## 8. 后续架构优化路线

## 8.1 历史评分卡与多人比较记录

对比视图按 `resume.scoreCard` 是否存在区分真实评分与演示评分；没有评分卡的示例档案或未完成分析的 PDF 都使用演示分值。图表汇总和表格逐行使用同一判定，不能只根据 `source` 字段推断分数是否真实。

评分链路和自由文本报告分开保存。`generateScoreCard()` 输出六项 0-100 分和每项最多三条简历证据；置信度计算暂时关闭，不允许模型直接输出综合分。服务端使用 `shared/scoring.ts` 的 `calculateComposite()` 按权重计算综合分：

```text
综合分 = Σ(单项分数 × 单项权重) / Σ(单项权重)
```

默认权重为：领导力 18%、专业能力 24%、经验 20%、经历广度 10%、岗位契合度 23%、进步分 5%。权重输入会被归一化为合计 100%，并保存到 `.metadata/settings.json`；评分卡同时保存实际使用的权重，保证历史结果可追溯。权重调整 Agent 使用 `server/skills/scoring-adjustment.md`，只允许调整现有六个工作相关维度，并要求说明含糊指令所采用的假设。AI 方案必须由审核员确认后才写入设置。

“经历广度”只表示与工作相关的行业、领域、方法和团队经历广度。系统禁止根据性别、民族、年龄、国籍、残障、宗教、婚育等受保护属性评分，也不会从姓名、照片或类似线索推断这些属性。

评分相关接口：

- `GET /api/resumes/scoring/weights`：读取当前权重。
- `PUT /api/resumes/scoring/weights`：提交手动调整后的权重。
- `POST /api/resumes/scoring/weights/adjust`：提交自然语言指令和当前权重，由专用 Skill Agent 返回归一化的六项权重及调整理由；此接口只返回建议，不写入配置。前端基于候选人已有单项分数预览综合分变化，并只在同岗位族候选人中计算排名变化，同时标出示例档案数量。用户确认后再调用 `PUT` 保存。

导入时如果模型可用，初始分析报告和 `scoreCard` 并行请求；手动岗位分析则在可选联网检索结束后，并行生成分析报告和按新职位要求评估的评分卡。并行只减少等待时间，不改变成功条件：只有两项都返回后才写入候选人记录和评分历史；任一调用失败时不会保存半套新结果。前端分析文档显示综合分、六项分数和一条代表性证据；多人对比视图读取候选人的评分卡，按服务端公式重新计算并排序，以数值条辅助横向扫描。选中候选人的证据摘要可点击回到单人分析，并尝试在 PDF 原文中精确定位；没有命中时由 PDF 阅读器报告未定位，不将相似句子伪装成来源。示例候选人在没有真实评分卡时使用固定演示分数，导入真实 PDF 后会被真实评分卡替换。

多人对比的当前排名依据默认为综合分，也可切换到六项能力中的任意一项及高分 / 低分优先方向。额外的评分来源分段可选“全部 / 已生成评分卡 / 演示或待评分”，来源筛选先于排序应用，并同步过滤排名表与质量图；数量徽标来自候选人是否持久化了 `scoreCard`，不会根据当前展示的演示 fallback 分推断。质量图默认横坐标为经历广度、纵坐标为能力深度；审核员可以分别选择六项能力或能力深度（领导力、专业能力、经验、岗位契合度、进步分的算术平均）作为图表轴，两个轴不允许重复，切换时自动交换轴值。象限分界可在 20–80 分之间以 5 分步进调整，X、Y 轴共用此阈值；点击任一象限会按当前阈值筛选图表点和排名表，点击已选象限或“显示全部”可恢复。过滤规则为横轴状态在前、纵轴状态在后，达到阈值计为高分。四象限标签按“横高 / 纵高”关系描述，不假定特定业务含义。点内数字和选中点姓名按筛选后表格名次展示。气泡半径固定使用 `5 + composite / 10` 映射 0–100 分，不使用当前样本最高分做相对缩放，50 与 100 分参考圆分别为 20 和 30 CSS 像素直径。靠近或完全重合的点会保留真实坐标，不做视觉抖动；重叠时应通过下方排名表点选，选中点最后绘制并高亮。气泡颜色按候选人 ID 稳定映射，只用于帮助区分对象，不表示维度分数或招聘结果。`POST /api/resumes/comparison/rank-draft` 使用 `server/skills/comparison-rank-assistant.md` 将自然语言转为受限的评分来源筛选、排名维度、方向、图表轴、分界和象限；模型仅接收用户指令与当前视图参数，不发送候选人资料、简历或评分。未被指令修改的参数由当前状态保留，结果以草案展示并需审核员确认后才应用。服务端通过 `normalizeComparisonRankDraft` 白名单校验模型输出，并为旧响应缺少字段时保留当前参数；同轴和未知枚举会被拒绝。

排名表不再展示候选人评分置信度；点击任一单项分值会选中该候选人、滚动到对应证据卡并短暂高亮，键盘操作也能触发。证据卡显示分数和可点击证据；点击证据会沿现有路径回到 PDF 定位。历史候选人元数据中已有的置信度字段会被忽略，不参与计算或展示。

评分卡应被视为招聘辅助证据，而不是自动录用结论。后续可把证据扩展为页码、文本引用和模型版本，以支持逐条回溯、复评分和公平性审计。

## 8.2 分析文档中的可视化与项目拆解

分析文档在文本报告后追加三类审核辅助内容：

1. **能力雷达图**：只绘制领导力、专业能力、经验、经历广度、岗位契合度和进步分六项分数，不把综合分混入雷达图，避免把加权结果误解为单项能力。
2. **综合分复评记录**：纵轴为每次真实保存的综合分，横轴为导入或复评时间。后端将每次成功生成的评分卡连同当时权重和岗位要求追加到候选人元数据的 `scoreHistory`。点击数据点可查看该次六项分数、分数相对上一次的变化、评分证据和当时的岗位要求；历史分数保持原始权重口径，不随当前权重修改而被静默重算。首次导入只有一个数据点，需在补充新材料后重新分析才能形成趋势。旧记录若没有历史数组，会以其现存评分卡作为单次导入记录，不回造早期分数。示例简历明确显示无真实评分历史。
3. **项目拆解·人话版**：规则版优先使用结构化工作经历中的公司、岗位、周期和详情；对没有结构化经历的 PDF，则从文本中提取“负责、主导、搭建、优化、交付、提升”等项目句子。每个项目展示原始名称、通俗名称、要解决什么、具体做了什么和带来什么结果。点击“AI 人话拆解”可用专用 Skill 生成同一结构的解释草案；草案另有视图切换，不覆盖规则版或简历数据。AI 为每项提供一条原文引文，点击引文复用 PDF 定位状态。

规则版术语翻译在前端采用可解释的词典规则（例如 SaaS、API、ETL、CI/CD、微服务、数据中台、留存分析）；AI 版调用 `server/skills/project-breakdown.md`，按需只传递当前展示的最多 4 条经历标题和内容，以及审核员可选的 500 字侧重点，不传候选人姓名、整份简历或职位要求。服务端将单条标题限制为 240 字、原文限制为 2500 字，并把响应限制为最多 4 项；`normalizeProjectBreakdownDraft()` 只接受有效且不重复的来源序号，并要求每项 `evidence` 至少 6 个 Unicode 字符且是该来源文本的精确子串，否则丢弃该项。目标、个人行动或结果缺乏原文支撑时，Skill 要求明确写成待核实信息；侧重点只能调整表述风格或强调已有证据，不能覆盖证据边界。前端显示置信度和未保存草案，侧重点变化会清除旧草案，切换候选人会卸载并重置草案；网络错误或模型未配置不影响规则版。引用继续进入统一 PDF 定位流程，若 PDF 文本层无法精确找到引文，会显示未定位提示，不将 AI 草案视为已核实证据。

`POST /api/agent/project-breakdown` 接收 `{ projects: [{ title, content }], reviewerFocus? }`，要求 1–4 个非空条目；标题和内容在传给模型前按字符截断，侧重点 trim 后最多 500 字。返回 `{ projects: [{ sourceIndex, title, plainTitle, goal, actions, outcome, evidence, confidence }] }`。`title` 由服务端从输入源恢复，模型不能改写来源身份。此接口不持久化结果，也不改变评分卡。

## 8.3 竞赛、期刊与公司资料库

资料库是招聘工作台中的独立工作区入口，和多人候选人对比一样替换中间到右侧的分析区域，左侧简历库继续保留。当前版本使用 `shared/knowledge.ts` 的本地种子资料，分为 `competition`、`journal` 和 `company` 三类；每条记录包含别名、领域、组织、地区、摘要、可核验信号、官方链接和人工含金量评估。

资料来源以 `evidenceSources` 随每条记录保存，字段包括 `id`、`title`、`url`、`sourceType`、`dataYear`、`note`、`verified` 和 `checkedAt`。输入最多保留 12 条，URL 仅允许 HTTP(S)，重复地址会折叠。修改来源名称、网址、类型或数据年份会清除其人工核对标记。旧记录的 `officialUrl` 继续作为官网入口展示，但不视为一条已核实指标或认定证据。来源覆盖图统计有来源、有已核来源、暂无来源三类记录，并可点击筛选列表。

服务端接口：

- `GET /api/resumes/knowledge`：读取资料记录，并合并本地人工评估。
- `POST /api/resumes/knowledge/filter-draft`：把自然语言映射为资料类别、核验状态、来源覆盖、评分区间、关键词、是否仅看简历引用及排序；只给模型发送指令，不发送简历或资料记录。服务端按枚举白名单校验草案，客户端展示预计命中数并等待审核员应用。
- `POST /api/resumes/knowledge`：新增自定义资料记录，写入本地 JSON 数据文件。
- `POST /api/resumes/knowledge/enrich`：根据表单字段、资料类别和审核员整理重点生成建议草稿；配置 Tavily 时只查询资料背景。响应包含建议字段、置信度、待核验项、来源和检索状态，不修改本地记录。
- `PUT /api/resumes/knowledge/:id`：修订名称、类别、别名、领域、组织、地区、简介、审核信号、官网入口和可追溯来源。种子记录的修订副本保存在本地自定义记录文件中，并按 id 覆盖种子显示值。
- `PUT /api/resumes/knowledge/:id/review`：保存 0-100 的人工含金量评分、审核备注、人工核验状态和本次引用的来源 ID，并追加一条审核快照。
- `POST /api/resumes/knowledge/:id/suggest`：用资料名称、领域和组织向 Tavily 查询公开背景；将最多 5 条经 URL 校验与摘要截断的搜索结果交给 `server/skills/knowledge-assessment.md`，返回初步评分、置信度、理由、核验问题和来源链接；只返回建议，不自动保存。查询失败时仍尝试仅依据本地资料生成建议，并返回明确状态。

评分不是客观排名。竞赛需要区分参赛、获奖、赛区、名次和年份；期刊/会议需要核对文章类型、作者贡献和正式发表状态；公司经历需要回到团队、职责、项目结果和个人贡献，不能用公司名气替代能力判断。自定义资料保存在 `.data/resumes/.metadata/knowledge-records.json`，人工评估文件保存在 `.data/resumes/.metadata/knowledge-reviews.json`，后续可以替换为 SQLite 或经过授权的组织数据库。

每次显式保存人工评估时，`knowledge-reviews.json` 会追加一条 `reviewHistory` 快照，包含分数、当时的评估备注、核验状态、ISO 时间、来源类型（人工填写或 AI 建议经人工确认）、被引用的来源 ID 和完整来源快照。来源快照固定保存标题、URL、类别、年份、说明及人工核对状态，因此后续编辑或删除资料不会改写历史依据。AI 建议生成阶段不写历史；只有审核员点击保存才形成记录。每条资料仅保留最近 30 条快照，最新分数仍由同一记录的当前字段提供。历史评估没有历史数组时保持为空，不根据当前值伪造历史。资料详情的评分折线按 ISO 时间正序排列，并以实际经过时长映射横坐标；全部记录时间相同或含无法解析时间时采用等距布局。点击数据点可查看当次备注、核验状态和引用来源快照，来源链接可直接打开，键盘也可在数据点间操作。

资料库概览按类别展示条目数及占比，点击类别图即可筛选列表；另有 0–49、50–69、70–84、85–100 四个评分段，展示各段条目数并支持点击筛选，重复点击或“清除筛选”恢复列表。评分段分布固定基于全部资料，不随关键词、类别或核验状态筛选变化，保证视觉分母稳定；评分段只描述当前记录的人工含金量评分，不能解读为客观排名。名称、评分和最近更新时间排序只改变展示顺序，不改写资料。概览中的“核验均分”只聚合人工状态为“已核验”的条目；没有已核验样本时显示“均分待积累”，不会把演示种子分数统计为人工结论。列表同时标记每条资料的待核验/已核验状态，并显示当前筛选命中数；存在筛选时可一键清除全部筛选条件。

资料库和简历支持双向交叉引用。分析文档的资料引用由简历正文与当前资料列表的标题/别名做确定性字符串匹配生成，不扫描候选人姓名或岗位字段，也不使用模型猜测关联；点击匹配项会打开资料库并定位到该记录。资料详情页反向列出命中的候选人和实际命中词；点击候选人会回到该简历，并将命中词交给 PDF 阅读器按页精确查找和高亮，示例简历则直接标色。PDF 中无法精确定位时沿用“未定位”提示，不把数据库字符串命中当作 PDF 证据。编辑别名或条目后，分析报告、资料列表和反向引用使用同一份已加载的记录状态，并在重新加载时从服务端恢复。没有命中时仍保留打开资料库的入口。后续如果把人工确认的引用持久化，应新增显式关系记录（candidateId、knowledgeId、evidence、reviewerConfirmed），不能把字符串命中直接当作已核实事实。

AI 资料评估由 `server/skills/knowledge-assessment.md` 约束。配置 Tavily 时，只用资料条目的名称、领域、组织和类别发起公开背景搜索，不发送候选人简历；最多将 5 条搜索标题、URL 和截断摘要提供给模型。每条结果经过 HTTP(S) URL 校验并去重，但它仍只是搜索摘要，不能证明页面当前可访问、官方身份或摘要准确。AI 需要区分本地记录与搜索线索，不得把赛事/期刊/公司背景外推为候选人的获奖、作者贡献或个人产出。审核员可补充岗位背景和最多 500 字的自然语言评估侧重，明确希望优先核对的证据；服务端截断输入，Skill 明确规定这类偏好不能覆盖证据要求、编造事实或消除不确定性。响应包括 0-100 建议分、0-1 置信度、简短理由、最多三个核验问题、来源链接和检索状态。没有配置搜索、没有结果或请求失败时仍可基于本地字段给建议，并在界面明确说明降级状态。AI 结果先作为独立提案展示，与当前评分草稿的分差和理由一并呈现；只有审核员选择“采用建议”才写入未保存草稿，随后仍须显式保存才能追加审核历史。若审核员保留当前草稿，AI 提案不会覆盖评分或备注。核验状态只代表人工记录。模型不可用时人工评分、核验状态和备注仍可独立使用。

资料录入草案由 `server/skills/knowledge-enrichment.md` 约束。`POST /api/resumes/knowledge/enrich` 接受资料名称、类别、现有表单字段和最多 300 字的审核员整理重点；可选使用 Tavily 查询标题、组织、领域和类别，最多传递 5 条公开搜索线索，不发送候选人资料。模型只返回背景字段、别名、审核信号、0-1 置信度、理由和待核验项，不允许给出含金量评分或核验状态。推荐官方 URL 必须与检索结果 URL 完全匹配，且应明确属于资料主体官网；无法判断时返回空。界面展示来源标题和截断摘要。草案保存生成时的表单指纹，若用户在等待期间修改任意输入或整理重点，则草案不能套用，需重新生成。审核员可以只补空白项或采用非空建议字段；两种操作都只修改前端草稿，仍需人工检查并显式保存。未知字段保持空白，不覆盖已有非空值。检索缺失或失败时可仅据现有字段生成建议，并显示降级状态。

通用 Agent 与资料核验共享 `server/web-search.ts`，以统一 Tavily 结果校验、限时和截断策略。服务进程对规范化查询做两分钟、最多 100 项的内存缓存，并合并并发的相同查询；失败请求不缓存。Agent 同一轮最多并行执行 4 个独立搜索调用，超出的调用会收到合并查询提示，单项失败会作为工具结果交还模型，让 Agent 有机会基于已有材料继续回答。扩展其他公开检索源时，应保持 `PublicSearchResult` 的标题、URL、摘要数据契约，并保留来源展示及检索状态。

## 8.4 历史招聘基准与百分位

`shared/history.ts` 提供只读演示种子；审核员新增的匿名样本保存在 `.data/resumes/.metadata/history-candidates.json`，不进入 Git。`GET /api/resumes/history` 合并演示与本地样本，并以 `source` 字段区分二者；只有 `source=local` 的记录可修改或删除。管理界面和分析报告使用同一份从服务端加载的数据状态。

历史样本管理接口：

- `GET /api/resumes/history`：读取演示种子和本地样本。
- `POST /api/resumes/history`：新增本地样本。
- `PUT /api/resumes/history/:id`：修改本地样本；演示样本只读。
- `DELETE /api/resumes/history/:id`：删除本地样本；演示样本只读。

每条样本只包含匿名代号、岗位、年份、综合分、首轮通过与最终录取状态，不保存简历正文或附件。服务端校验年份与 0-100 分数，并拒绝“未通过首轮但最终录取”的矛盾状态。正式使用需确保历史指标已授权并去标识化；管理界面会把演示记录标为只读，把本地录入标为可维护。

分析文档将同一量尺上的当前候选人分数、首轮通过样本、最终录取样本和未通过首轮样本绘制成分布点图。年份筛选只作用于当前岗位族，点击样本点可查看年份、匿名代号、分数及流程结果；中文岗位族标签由 `roleGroupLabel()` 提供。历史样本管理页展示按岗位族和年份筛选的结果分布，图中散点与记录条目可互相选中；本地记录支持新增、修改和二次确认后删除，演示记录保持只读。当前种子样本使用虚构代号，界面明确标注其为演示数据；接入真实招聘数据前必须取得授权、去标识化并记录评分口径与年份。

历史样本管理页还提供五档综合分直方概览（0–19、20–39、40–59、60–79、80–100）。每档按最终录取、仅通过首轮、未通过首轮堆叠，条形总长度按当前岗位 / 年份样本数缩放。点击档位或结果图例会筛选摘要指标、点图和样本列表；分数段与结果状态取交集，再次点击结果图例恢复“全部结果”，改变岗位或年份会清除此档位筛选。移动端采用两列分布卡，保持档位和结果标签可读。

历史样本库的自然语言筛选助手只接收用户指令和当前可用的岗位族 / 年份选项，不读取候选人记录。`POST /api/resumes/history/filter-draft` 通过 `server/skills/history-filter-assistant.md` 将指令转换成受限 JSON（岗位族、年份、分数段、招聘结果和理由）；服务端将每个值与允许选项核对，页面先展示草案，只有用户点击“应用筛选”才改变当前列表。请求不修改或新增任何招聘记录。

候选人分析完成后，系统按岗位族筛选历史样本，并计算：

- `sampleRoleGroup`：实际参与比较的岗位族；当前候选人所属岗位族无样本时为 `all`，使用全部岗位族作回退，并在报告卡片中明确标出。
- `percentile`：综合分严格低于当前分数的历史样本比例，同分样本不计入“超过”；没有历史样本时为 `null`，不显示虚构百分位。
- `screenCutoff`：有首轮通过样本时取其中位数综合分；样本包括首轮通过且最终录取者，也包括通过首轮但未录取者。没有首轮通过样本时为 `null`，不再回退到全体分数。
- `hireCutoff`：有最终录取样本时取其中位数综合分；没有最终录取样本时为 `null`，不再回退到全体分数。

参考线中位数先按综合分升序排列；奇数样本取中间值，偶数样本取中间两值的算术平均值，最终保留一位小数。可视化的三个分布轨道互斥：最终录取、首轮通过未录取、未过首轮；每条轨道展示该结果组样本数。首轮参考线的 `n` 则按全部首轮通过样本计算，因此可能大于“首轮通过未录取”轨道的样本数。
- `screenedRate` / `hiredRate`：样本中的首轮通过率和录取率。

分析报告用黄色百分比标记展示“超过历史样本 X%”，只统计分数严格低于当前分数的样本，同分不会被误算为超过；同时显示样本量和实际比较岗位范围。当前岗位族没有样本时，计算回退到全部岗位，卡片会写明回退口径，“查看当前样本库”也会预选全部岗位而不是原岗位族；如果所选年份在岗位族有可用记录，则报告和样本库使用同一年份。没有历史样本时百分位显示不可比较；缺少首轮通过或录取结果样本时，对应参考线显示“暂无该类样本”，不会借用全体候选人中位数。样本少于 10 份时，卡片明确提示单条记录可能明显影响百分位和参考线。从分布图点选样本后再打开样本库，会继续选中同一条记录，便于从点位追到完整样本行。审核员可继续按分数区间和招聘结果交叉筛选；页面切换不改写候选人或样本数据。百分位是辅助比较，不是录用规则；岗位族、年份、评分权重或模型版本变化时，应重新计算并在记录中保留口径。

### 分析工作区的离线边界

候选人分析链路只使用 PDF 原文、OCR 文本、候选人字段和固定评分规则。竞赛、论文、项目及公司经历不会联网查询、不会读取资料库背景、不会调用搜索工具，也不会据此判断候选人是否真实获奖、发表或参与。资料库仍可由审核员独立打开并手动维护，但其内容不会自动回写候选人分析。

分析文档同时保留三种互补视图：六项能力雷达图用于观察形状，综合分时间折线用于观察真实复评变化，综合分贡献拆解用于解释 `score × weight / totalWeight` 的来源。贡献拆解的条形长度表示单项分数，贡献值表示进入综合分的实际分值。雷达图的能力顶点、维度标签及贡献条均可选择同一评分维度；选中后会显示该维度的分值和评分证据。点击证据会调用统一的 PDF 定位状态，尝试在原文中搜索并高亮；无法精确命中时沿用未定位提示，不声称证据已被原文验证。控件支持键盘选择，切换候选人会清除旧的维度选择。趋势图保留独立的历史评估选择及历史证据查看，不与当前评分卡的维度选择混淆，从而形成“评分维度 → 评分证据 → PDF 原文”的交叉审计路径。

分析工作区提供固定的常用任务模板，模板只替换用户问题，不改变职位要求和评分权重。分析任务旁的“优化任务”通过 `POST /api/agent/task-draft` 调用 `server/skills/analysis-task-assistant.md`，只将当前任务文本（服务端最多接收并处理 1000 字）发送给模型，不发送简历、候选人姓名或职位要求。服务端使用 JSON 模式并将草案限制在 800 字以内；前端展示草案及理由，只有审核者点击采用才替换分析任务，继续编辑原任务或点击保留都不会改写内容。该步骤是可选的额外模型往返，不影响直接分析及固定快捷任务。Skill 保留任务原意、禁止增加候选人事实和敏感属性要求，并把简历中的文字视为非可信数据。任何由 AI 提出的权重或资料评分仍先进入草稿，必须人工确认并显式保存；联网开关属于用户可见的请求参数，不由模型自行开启。

职位要求输入旁的“整理岗位重点”调用 `server/skills/job-profile.md`，只对招聘人员已经输入的文本做去重、分组和结构化，不补写岗位事实，也不参与候选人评分。服务端通过 `POST /api/agent/role-profile` 返回 `requirements` 和 `rationale`；前端先显示草案，只有点击采用才替换输入框内容，原文可以通过保留操作继续使用。这样职位要求、分析任务、评分权重和排名依据等可交互参数都有明确的人工确认边界。

### OCR

当 `text` 为空或字符密度异常时，把 PDF 页面送入 OCR 适配器，保存 `textSource: "ocr"`、语言和置信度。OCR 应是 `extractText()` 的可替换实现，不应改变前端和报告 API。

### 异步任务队列

将同步 `POST /api/resumes` 拆成：保存文件、创建 `jobId`、后台执行解析。新增 `processingStatus`（`queued`、`extracting`、`identifying`、`reporting`、`complete`、`failed`），前端轮询或使用 SSE。现有 `analysisStatus` 继续表示报告结果，不与任务状态混用。

### 模型与提示词版本

在元数据中保存 `modelName`、`promptVersion`、`skillVersion`。当模型或 Skill 变更时，支持只重跑字段提取、只重跑报告或全部重跑，而不是无差别覆盖所有缓存。

### 可审计证据

将报告中的事实绑定到页码和文本片段，例如 `{ claim, page, quote }`。当前前端已支持评分历史中的证据点击定位：PDF.js 文字层按页保留文字块坐标，点击依据后先做去空格和标点的精确归一化匹配，匹配成功则滚动到对应页并以绿色覆盖高亮；没有精确匹配时显示“尚未在 PDF 原文中精确定位”，不使用模糊相似度伪造位置。后续可让服务端在 `ScoreEvidence` 中直接返回页码、原文引用和字符范围，进一步减少前端二次匹配。

### 多租户与权限

当前服务只监听本机回环地址，适合单机工作台。若部署到共享服务器，必须在文件目录、候选人 API、模型调用和审计日志层加入用户隔离、访问控制、加密存储和删除策略。

## 9. 维护检查清单

- PDF.js CMap 和标准字体资源能由开发服务器返回。
- 文本型中英文 PDF 都能提取文字；扫描件明确显示需要 OCR。
- 模型未配置时导入仍能保存和阅读，状态为 `unavailable`。
- 模型超时时 PDF 不丢失，状态为 `failed`，且可以重试。
- `analysisReport` 不为空时，右侧分析文档可以恢复显示。
- PDF 阅读器的奖项标注开关可以一次性显示或隐藏当前 PDF 的全部命中项。
- `.env`、`.data/` 和生成的 PDF.js 静态资源不进入 Git。
- `npm test` 验证搜索缓存的并发去重、返回结果隔离和失败重试行为。
- `shared/scoring.test.ts` 验证不同分界值下质量图象限的坐标、尺寸和标签中心一致。
