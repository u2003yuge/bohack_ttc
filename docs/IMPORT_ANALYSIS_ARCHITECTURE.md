# 简历导入与自动分析链路

本文说明 Bohack 当前的简历导入、PDF 阅读、候选人识别和分析报告生成架构。目标是让后续接入 OCR、任务队列、更多模型或数据库时，可以保持前端交互和数据契约稳定。

## 1. 设计目标与边界

导入一份 PDF 的结果不是单纯的文件复制，而是一个可追踪的候选人索引任务：

1. 保留原始 PDF，保证阅读器可以随时打开原文件。
2. 从 PDF 提取可检索文本，保留原始文本供分析和审计。
3. 从文本中提取最小候选人字段，用于左侧候选人列表。
4. 自动生成一份不依赖职位描述的初始分析报告。
5. 后续输入职位要求时，在同一候选人记录上生成岗位匹配报告。
6. 任何模型失败都不能破坏原文件，也不能伪造成功结果。

当前版本是本地优先架构：PDF、文本和分析缓存位于 `RESUME_DIR`，默认是 `.data/resumes`。模型 API Key 只由服务端读取。浏览器只访问本地 API，不直接接触密钥。

## 2. 端到端流程

```text
浏览器选择 PDF / 文件夹
        |
        v
POST /api/resumes  (application/pdf)
        |
        +--> 校验大小、文件头、文件名并写入 <RESUME_DIR>/<id>.pdf
        |
        +--> PDF.js Node 提取每页文本
        |       - CMap: pdfjs-dist/cmaps
        |       - 标准字体: pdfjs-dist/standard_fonts
        |
        +--> extractCandidate()
        |       - 只允许从原文提取 name/role/location/education/skills/summary
        |       - JSON 结构化输出
        |
        +--> generateInitialReport()
        |       - 使用简历 Skill
        |       - 不给岗位匹配分，不调用网页搜索
        |       - 输出概览、证据、信息缺口、建议追问
        |
        +--> 写入 <RESUME_DIR>/.metadata/<id>.json
        |
        +--> 返回 ResumeRecord
```

导入请求是同步请求，因此前端在模型链路结束前显示“正在识别”。这保证导入完成时左侧候选人、分析文档和持久化元数据一致；代价是模型较慢时导入按钮会等待。后续应将这一步迁移为异步任务，但保留同样的记录字段和状态。

## 3. 文件与元数据

每份简历有一个稳定的 `id`，由原始文件名片段、时间戳和随机短 ID 组成。原始 PDF 与元数据分离：

```text
.data/resumes/
  <id>.pdf
  .metadata/
    <id>.json
```

当前 `ResumeRecord` 的核心字段：

| 字段 | 用途 |
| --- | --- |
| `id` / `fileName` | 文件与 API 路由定位 |
| `text` | PDF 文本提取结果，作为模型输入和检索基础 |
| `name` / `role` / `location` | 左侧候选人卡片和详情头部 |
| `education` / `skills` / `summary` | 候选人基础画像 |
| `analysisReport` | 最近一次自动或手动分析报告 |
| `analysisStatus` | `complete`、`failed` 或 `unavailable` |
| `analysisError` | 最近一次失败的可读原因 |
| `analyzedAt` | 报告生成时间 |
| `scoreHistory` | 按时间追加保存的真实评分卡快照、评估场景和岗位要求 |
| `extractionVersion` | 解析器升级后的缓存失效标记 |

`extractionVersion` 变更时，服务会重新提取已有 PDF 并刷新元数据。这个机制用于部署 CMap、OCR 或提示词升级，不需要用户重新导入文件。

## 4. 状态与失败处理

当前状态语义如下：

- `complete`：文本提取成功，并且初始分析报告已生成。
- `failed`：PDF 可保存和阅读，但模型字段提取或报告生成失败；`analysisError` 保留原因，前端显示“重试分析”。
- `unavailable`：没有配置模型服务，PDF 仍可阅读，候选人字段回退到文件名或默认值。

失败的处理原则：

1. 文件写入成功后才开始解析；解析失败会删除刚写入的 PDF，避免留下半条记录。
2. 模型失败不会删除 PDF，也不会把空字符串标记成成功报告。
3. 手动重试调用 `POST /api/resumes/:id/analyze`，只更新分析字段，不重复复制 PDF。
4. 读取目录时按 `extractionVersion` 判断是否需要重建索引。

## 5. API 契约

### `POST /api/resumes`

请求头：`Content-Type: application/pdf`、`X-File-Name: encodeURIComponent(originalName)`。

成功返回 HTTP `201` 和完整 `ResumeRecord`。导入过程包含文本提取和初始报告生成，因此返回时 `analysisStatus` 已有明确值。

### `GET /api/resumes`

扫描 `RESUME_DIR` 中的 PDF，读取或重建元数据，返回 `{ directory, resumes }`。该接口是工作台启动和刷新时的索引入口。

### `POST /api/resumes/:id/analyze`

请求体：`{ roleRequirements: string, question: string }`。使用已缓存的 `text` 生成岗位分析报告，成功后更新 `analysisReport`、`analysisStatus` 和 `analyzedAt`。

### `GET /api/resumes/:id/file`

只返回原始 PDF 流，阅读器使用 PDF.js 在浏览器内渲染。CMap 和标准字体由 Vite 静态目录提供，不混入 PDF 文件接口。

## 6. PDF 透明文字层与奖项遮罩

PDF 阅读器在原始画布上方维护一个透明的文字层。文字层使用 PDF.js `getTextContent()` 返回的每个文本项和 viewport 变换矩阵，将 PDF 坐标转换为浏览器 CSS 像素坐标。原始画布负责显示 PDF；文字层只负责选择和标注，不替换或重绘原文。

奖项识别是当前版本的轻量规则层：对文本项匹配中文奖项词、竞赛词和常见英文缩写，例如“奖”“金牌”“一等奖”“竞赛”“ACM”“ICPC”“CCF”“CSP”。识别结果只用于视觉提示，不代表语义判断，也不会改变候选人字段或分析报告。

遮罩交互只有一个左右拨动开关 `showAwardMask`（使用 `role="switch"`，视觉上不是复选框）：

- 开启：当前 PDF 中所有命中的文本项显示半透明黄色背景。
- 关闭：隐藏当前 PDF 的全部黄色背景，但保留透明文字层和原始 PDF。
- 开关只影响当前阅读器视图，不修改 PDF 文件、候选人元数据或分析报告。

渲染约束：

1. 标注层必须与对应页面 canvas 使用同一 viewport、缩放比例和输出像素比例。
2. 每个页面独立维护文本项，翻页和滚动只更新当前页指示器，不改变标注集合。
3. 文本项没有可用坐标时不创建标注，避免出现漂移的黄色块。
4. 规则命中数量仅作为界面提示，用户仍需阅读原始 PDF 核对奖项内容。

## 7. 模型分层

模型调用分为两个目的，不能混成一个不透明提示词：

1. `extractCandidate`：低温度、JSON 输出、字段少、只读原文；用于列表展示。
2. `generateInitialReport`：没有职位要求，输出候选人概览和证据；导入时自动运行。
3. `generateRoleReport`：接收职位要求和用户问题，输出匹配分析；用户点击分析或重试时运行。

三个阶段共享 `server/skills/resume-analysis.md` 的安全与证据规则，但输入和输出职责不同。任何阶段都将简历放在 `<resume>` 标记中，并把简历视为不可信数据，避免执行 PDF 中可能出现的提示注入内容。

## 8. 后续架构优化路线

## 8.1 Agent 评分卡与多人比较

评分链路和自由文本报告分开保存。`generateScoreCard()` 只输出六项 0-100 分、每项最多三条简历证据和 0-1 置信度；不允许模型直接输出综合分。服务端使用 `shared/scoring.ts` 的 `calculateComposite()` 按权重计算综合分：

```text
综合分 = Σ(单项分数 × 单项权重) / Σ(单项权重)
```

默认权重为：领导力 18%、专业能力 24%、经验 20%、经历广度 10%、岗位契合度 23%、进步分 5%。权重输入会被归一化为合计 100%，并保存到 `.metadata/settings.json`；评分卡同时保存实际使用的权重，保证历史结果可追溯。权重调整 Agent 使用 `server/skills/scoring-adjustment.md`，只允许调整现有六个工作相关维度，并要求说明含糊指令所采用的假设。AI 方案必须由审核员确认后才写入设置。

“经历广度”只表示与工作相关的行业、领域、方法和团队经历广度。系统禁止根据性别、民族、年龄、国籍、残障、宗教、婚育等受保护属性评分，也不会从姓名、照片或类似线索推断这些属性。

评分相关接口：

- `GET /api/resumes/scoring/weights`：读取当前权重。
- `PUT /api/resumes/scoring/weights`：提交手动调整后的权重。
- `POST /api/resumes/scoring/weights/adjust`：提交自然语言指令和当前权重，由专用 Skill Agent 返回归一化的六项权重及调整理由；此接口只返回建议，不写入配置。前端基于候选人已有单项分数预览综合分变化，并只在同岗位族候选人中计算排名变化，同时标出示例档案数量。用户确认后再调用 `PUT` 保存。

导入时如果模型可用，会在初始分析报告旁生成 `scoreCard`；手动岗位分析会用新的职位要求刷新评分卡。前端分析文档显示综合分、六项分数、置信度和一条代表性证据；多人对比视图读取候选人的评分卡，按服务端公式重新计算并排序。示例候选人在没有真实评分卡时使用固定演示分数，导入真实 PDF 后会被真实评分卡替换。

评分卡应被视为招聘辅助证据，而不是自动录用结论。后续可把证据扩展为页码、文本引用和模型版本，以支持逐条回溯、复评分和公平性审计。

## 8.2 分析文档中的可视化与项目拆解

分析文档在文本报告后追加三类审核辅助内容：

1. **能力雷达图**：只绘制领导力、专业能力、经验、经历广度、岗位契合度和进步分六项分数，不把综合分混入雷达图，避免把加权结果误解为单项能力。
2. **综合分复评记录**：纵轴为每次真实保存的综合分，横轴为导入或复评时间。后端将每次成功生成的评分卡连同当时权重和岗位要求追加到候选人元数据的 `scoreHistory`。点击数据点可查看该次六项分数、分数相对上一次的变化、评分证据和当时的岗位要求；历史分数保持原始权重口径，不随当前权重修改而被静默重算。首次导入只有一个数据点，需在补充新材料后重新分析才能形成趋势。旧记录若没有历史数组，会以其现存评分卡作为单次导入记录，不回造早期分数。示例简历明确显示无真实评分历史。
3. **项目拆解·人话版**：优先使用结构化工作经历中的公司、岗位、周期和详情；对没有结构化经历的 PDF，则从文本中提取“负责、主导、搭建、优化、交付、提升”等项目句子。每个项目展示原始名称、通俗名称、要解决什么、具体做了什么和带来什么结果。术语翻译只用于阅读辅助，原始名称和原文证据仍保留，审核员需要据此复核。

当前术语翻译在前端采用可解释的词典规则（例如 SaaS、API、ETL、CI/CD、微服务、数据中台、留存分析），后续可将其替换为受控的 Agent 翻译步骤，并保存原文、译文、模型版本和证据来源。

## 8.3 竞赛、期刊与公司资料库

资料库是招聘工作台中的独立工作区入口，和多人候选人对比一样替换中间到右侧的分析区域，左侧简历库继续保留。当前版本使用 `shared/knowledge.ts` 的本地种子资料，分为 `competition`、`journal` 和 `company` 三类；每条记录包含别名、领域、组织、地区、摘要、可核验信号、官方链接和人工含金量评估。

服务端接口：

- `GET /api/resumes/knowledge`：读取资料记录，并合并本地人工评估。
- `POST /api/resumes/knowledge`：新增自定义资料记录，写入本地 JSON 数据文件。
- `PUT /api/resumes/knowledge/:id`：修订名称、类别、别名、领域、组织、地区、简介、审核信号和来源链接。种子记录的修订副本保存在本地自定义记录文件中，并按 id 覆盖种子显示值。
- `PUT /api/resumes/knowledge/:id/review`：保存 0-100 的人工含金量评分、审核备注和人工核验状态，并追加一条审核快照。
- `POST /api/resumes/knowledge/:id/suggest`：用资料名称、领域和组织向 Tavily 查询公开背景；将最多 5 条经 URL 校验与摘要截断的搜索结果交给 `server/skills/knowledge-assessment.md`，返回初步评分、置信度、理由、核验问题和来源链接；只返回建议，不自动保存。查询失败时仍尝试仅依据本地资料生成建议，并返回明确状态。

评分不是客观排名。竞赛需要区分参赛、获奖、赛区、名次和年份；期刊/会议需要核对文章类型、作者贡献和正式发表状态；公司经历需要回到团队、职责、项目结果和个人贡献，不能用公司名气替代能力判断。自定义资料保存在 `.data/resumes/.metadata/knowledge-records.json`，人工评估文件保存在 `.data/resumes/.metadata/knowledge-reviews.json`，后续可以替换为 SQLite 或经过授权的组织数据库。

每次显式保存人工评估时，`knowledge-reviews.json` 会追加一条 `reviewHistory` 快照，包含分数、当时的评估备注、核验状态、ISO 时间和来源类型（人工填写或 AI 建议经人工确认）。AI 建议生成阶段不写历史；只有审核员点击保存才形成记录。每条资料仅保留最近 30 条快照，最新分数仍由同一记录的当前字段提供。旧版评估没有历史数组时保持为空，不根据当前值伪造历史。资料详情的评分折线可点击数据点查看当次备注和核验状态，键盘也可在数据点间操作。

资料库概览按类别展示条目数及占比，点击类别图即可筛选列表；名称、评分和最近更新时间排序只改变展示顺序，不改写资料。概览中的“核验均分”只聚合人工状态为“已核验”的条目；没有已核验样本时显示“均分待积累”，不会把演示种子分数统计为人工结论。列表同时标记每条资料的待核验/已核验状态，并显示当前筛选命中数。

资料库和简历支持双向交叉引用。分析文档的资料引用由简历姓名、岗位和提取文本与当前资料列表的标题/别名做确定性字符串匹配生成，不使用模型猜测关联；点击匹配项会打开资料库并定位到该记录。资料详情页反向列出命中的候选人，点击候选人会回到该简历。编辑别名或条目后，分析报告、资料列表和反向引用使用同一份已加载的记录状态，并在重新加载时从服务端恢复。没有命中时仍保留打开资料库的入口。后续如果把人工确认的引用持久化，应新增显式关系记录（candidateId、knowledgeId、evidence、reviewerConfirmed），不能把字符串命中直接当作已核实事实。

AI 资料评估由 `server/skills/knowledge-assessment.md` 约束。配置 Tavily 时，只用资料条目的名称、领域、组织和类别发起公开背景搜索，不发送候选人简历；最多将 5 条搜索标题、URL 和截断摘要提供给模型。每条结果经过 HTTP(S) URL 校验并去重，但它仍只是搜索摘要，不能证明页面当前可访问、官方身份或摘要准确。AI 需要区分本地记录与搜索线索，不得把赛事/期刊/公司背景外推为候选人的获奖、作者贡献或个人产出。审核员可补充岗位背景和最多 500 字的自然语言评估侧重，明确希望优先核对的证据；服务端截断输入，Skill 明确规定这类偏好不能覆盖证据要求、编造事实或消除不确定性。响应包括 0-100 建议分、0-1 置信度、简短理由、最多三个核验问题、来源链接和检索状态。没有配置搜索、没有结果或请求失败时仍可基于本地字段给建议，并在界面明确说明降级状态。建议必须由审核员复核、调整并显式保存；核验状态只代表人工记录。模型不可用时人工评分、核验状态和备注仍可独立使用。

通用 Agent 与资料核验共享 `server/web-search.ts`，以统一 Tavily 结果校验、限时和截断策略。服务进程对规范化查询做两分钟、最多 100 项的内存缓存，并合并并发的相同查询；失败请求不缓存。Agent 同一轮最多并行执行 4 个独立搜索调用，超出的调用会收到合并查询提示，单项失败会作为工具结果交还模型，让 Agent 有机会基于已有材料继续回答。扩展其他公开检索源时，应保持 `PublicSearchResult` 的标题、URL、摘要数据契约，并保留来源展示及检索状态。

## 8.4 历史招聘基准与百分位

`shared/history.ts` 是当前版本的本地基准数据库种子，记录历史候选人的岗位族、年份、是否通过首轮筛查、是否最终录取和综合分。服务端以 `GET /api/resumes/history` 提供只读接口；后续可以将实现替换为 SQLite 或组织内部数据库，前端保持同一数据契约。

分析文档将同一量尺上的当前候选人分数、首轮通过样本、最终录取样本和未通过首轮样本绘制成分布点图。年份筛选只作用于当前岗位族，点击样本点可查看年份、演示姓名、分数及流程结果；中文岗位族标签由 `roleGroupLabel()` 提供。筛选年份没有样本时会回退到该岗位族的全部年份，并继续展示实际使用的样本数。当前种子样本使用虚构代号，界面明确标注其为本地演示数据；接入真实招聘数据前必须取得授权、去标识化并记录评分口径与年份。

候选人分析完成后，系统按岗位族筛选历史样本，并计算：

- `percentile`：当前综合分不低于多少比例的历史样本。
- `screenCutoff`：历史首轮通过样本的中位数综合分。
- `hireCutoff`：历史最终录取样本的中位数综合分。
- `screenedRate` / `hiredRate`：样本中的首轮通过率和录取率。

分析报告用黄色百分比标记展示“超过历史样本 X%”，同时显示样本量和参考线。百分位是辅助比较，不是录用规则；岗位族、年份、评分权重或模型版本变化时，应重新计算并在记录中保留口径。

### OCR

当 `text` 为空或字符密度异常时，把 PDF 页面送入 OCR 适配器，保存 `textSource: "ocr"`、语言和置信度。OCR 应是 `extractText()` 的可替换实现，不应改变前端和报告 API。

### 异步任务队列

将同步 `POST /api/resumes` 拆成：保存文件、创建 `jobId`、后台执行解析。新增 `processingStatus`（`queued`、`extracting`、`identifying`、`reporting`、`complete`、`failed`），前端轮询或使用 SSE。现有 `analysisStatus` 继续表示报告结果，不与任务状态混用。

### 模型与提示词版本

在元数据中保存 `modelName`、`promptVersion`、`skillVersion`。当模型或 Skill 变更时，支持只重跑字段提取、只重跑报告或全部重跑，而不是无差别覆盖所有缓存。

### 可审计证据

将报告中的事实绑定到页码和文本片段，例如 `{ claim, page, quote }`。前端可以点击报告证据跳到 PDF 对应页面，避免把自由文本评分当成不可解释结论。

### 多租户与权限

当前服务只监听本机回环地址，适合单机工作台。若部署到共享服务器，必须在文件目录、候选人 API、模型调用和审计日志层加入用户隔离、访问控制、加密存储和删除策略。

## 9. 维护检查清单

- PDF.js CMap 和标准字体资源能由开发服务器返回。
- 文本型中英文 PDF 都能提取文字；扫描件明确显示需要 OCR。
- 模型未配置时导入仍能保存和阅读，状态为 `unavailable`。
- 模型超时时 PDF 不丢失，状态为 `failed`，且可以重试。
- `analysisReport` 不为空时，右侧分析文档可以恢复显示。
- PDF 阅读器的奖项标注开关可以一次性显示或隐藏当前 PDF 的全部命中项。
- `.env`、`.data/` 和生成的 PDF.js 静态资源不进入 Git。
- `npm test` 验证搜索缓存的并发去重、返回结果隔离和失败重试行为。
